# WORK VITAL 카피·UX 라이팅 검토 기록

## 작업 기준

- 기준 문서: [writing-guide.md](writing-guide.md). 사용자가 편집한 최신 가이드를 반영했습니다.
- 원문: [copy-inventory.json](copy-inventory.json)의 `rows`. 각 ID로 원문·영역·표시 조건·출처·위치를 찾습니다.
- 대상: https://claude.ai/artifact/PDoCQjYmUNZMevge89onRq
- 수집일: 2026-10-29. 사용자 확인 기준 프로토타입입니다. 이 파일을 만들면서 화면을 다시 수집하지 않았습니다.
- 핵심 사용자 가정: 조직 진단을 검토하는 인사·조직개발 담당자. 실제 고객 검증 결과가 아닙니다.
- 범위: 메인과 메인 내부 진단 탭·메뉴. 다른 개별 페이지는 CTA 연결 확인 범위에서만 참고합니다.
- 기존 임시 E2E 테스트의 정확한 문구 일치를 카피 작성 제약으로 삼지 않습니다. 카피 반영 후 필요한 테스트를 업데이트합니다.
- 아래 수정안은 전문가 제안이며 사용자 승인·실제 화면 반영·효과 검증 전입니다. 기능과 정책을 임의 확정하지 않습니다.

## 상태 정의

| 상태 | 뜻 |
|---|---|
| 검토 제안 | 원문을 근거로 문제와 수정 가설을 기록함 |
| 사실 확인 필요 | 기능·정책·공식 용어·근거를 확인해야 문구 확정 가능 |
| 수정안 확정 | 사용자가 적용할 문안을 선택함 |
| 반영 완료 | 실제 홈페이지에 문안을 반영함 |
| 화면 확인 완료 | 반영한 문구와 표시 조건·연결 결과를 확인함 |
| 사용자 검증 완료 | 실제 사용자 관찰 결과를 별도로 기록함 |

현재 아래 항목은 모두 `검토 제안` 또는 `사실 확인 필요`입니다. 가이드의 예시에 사용되었다는 이유로 수정안 확정으로 처리하지 않습니다.

## 카피 검토 목록

### COPY-001 · 첫 설명에서 고객의 문제와 도움을 연결하기

- 상태: 검토 제안
- 우선순위: 높음
- 원문 ID: D-013
- 원문: “진단에서 개선까지, 조직 활력 플랫폼 WORK VITAL”
- 문제 근거: 진단·개선의 범주를 제시하지만, 독자가 어떤 상황에서 무엇을 얻는지 스스로 해석해야 합니다. 주변 설명까지 함께 보고 소개 문단 단위로 평가합니다.
- 적용 원칙: ① 고객의 문제와 이점, ② 짧고 구체적으로
- 수정안: “진단 결과를 받고도 무엇부터 개선할지 막막한가요? 부서별 결과를 비교해 개선 과제의 우선순위를 정하세요.”
- 기대 효과 가설: 인사 담당자가 자신의 업무와 서비스의 관련성을 더 쉽게 설명합니다.
- 검증 방법: 첫 소개를 읽은 뒤 누구를 위한 서비스이며 무엇을 돕는지 자신의 말로 설명하게 합니다.

### COPY-002 · 추상적인 가치 설명을 실제 사용 과정으로 풀기

- 상태: 검토 제안
- 우선순위: 높음
- 원문 ID: D-014
- 원문: “보이지 않던 조직의 상태를 가시화하고, 개선과 확인을 되풀이하여 몰입이 높은 조직을 만들어 갑니다.”
- 문제 근거: 무엇으로 상태를 파악하고 어떤 행동을 하는지보다 추상적인 결과를 앞세웁니다.
- 적용 원칙: ① 고객의 문제와 이점, ② 짧고 구체적으로, ⑤ 확인된 사실
- 수정안: “구성원 설문으로 조직 상태를 파악합니다. 개선 활동 후에는 무엇이 달라졌는지 확인합니다.”
- 기대 효과 가설: 사용자가 설문·결과 확인·변화 확인의 과정을 구체적으로 예상합니다.
- 검증 방법: 읽은 뒤 서비스의 사용 과정을 설명하게 하고 추가 설명이 필요한 부분을 기록합니다.

### COPY-003 · 기능 배지를 업무와 판단에 연결하기

- 상태: 검토 제안
- 우선순위: 높음
- 원문: “기대×만족 우선순위 도출”
- 원문 위치: 메인 첫 화면의 기능 배지. inventory에서 원문을 검색합니다.
- 문제 근거: 측정 개념과 명사를 압축해 무엇을 선택하거나 판단하게 되는지 알아보기 어렵습니다.
- 적용 원칙: ① 고객의 문제와 이점, ③ 사용자 언어, 명사 나열 풀어쓰기
- 수정안: “기대는 높지만 만족은 낮은 항목을 찾아, 먼저 개선할 과제를 정합니다.”
- 적용 메모: 짧은 배지의 표현과 이를 설명하는 문장의 길이는 구분해 판단합니다. 위 수정안을 배지 안에 그대로 넣어야 한다는 뜻은 아닙니다.
- 기대 효과 가설: 기능명을 몰라도 개선 우선순위를 정하는 데 쓰는 정보임을 이해합니다.
- 검증 방법: 해당 표현이 어떤 판단을 돕는지 설명하게 합니다.

### COPY-004 · 종단·횡단 표현을 고객의 비교 작업으로 풀기

- 상태: 검토 제안
- 우선순위: 높음
- 원문: “회차별(종단) 추이와 업계 평균을 한 화면에서 비교하고, 부서·직급·속성별(횡단) 차이까지 교차로 분석합니다.”
- 원문 위치: 메인 기능 ‘추이·비교 대시보드’
- 문제 근거: 비교할 대상보다 분석 용어가 이해 부담을 높일 수 있습니다. 전문성이 있는 독자에게도 고객의 질문부터 설명할 수 있습니다.
- 적용 원칙: ② 짧고 구체적으로, ③ 사용자 언어
- 수정안: “지난 조사 및 업계 평균과 결과를 비교합니다. 부서·직급별 차이도 함께 살펴봅니다.”
- 기대 효과 가설: 비교 가능한 대상을 더 쉽게 구분합니다.
- 검증 방법: 무엇과 무엇을 비교할 수 있는지 묻습니다.

### COPY-005 · 인재유지 모델을 직원 경험의 단계로 설명하기

- 상태: 검토 제안
- 우선순위: 중간
- 원문 ID: R-038
- 원문: “MOT 생애주기 7국면, 20 진단요인으로 측정합니다”
- 문제 근거: 모델명을 아는 독자에게는 정보가 되지만, 첫 방문자는 무엇을 조사하는지 먼저 파악하기 어렵습니다.
- 적용 원칙: ③ 사용자 언어
- 수정안: “입사부터 퇴직까지 7단계의 경험을 20개 요인으로 살펴봅니다.”
- 적용 메모: 필요한 공식 MOT 모델명은 첫 등장에 뜻을 설명하고 유지할 수 있습니다.
- 기대 효과 가설: 진단의 대상 범위를 쉽게 설명합니다.
- 검증 방법: 어떤 경험을 살펴보는 진단인지 묻습니다.

### COPY-006 · 분석 결과를 원인 확정처럼 표현하지 않기

- 상태: 사실 확인 필요
- 우선순위: 높음
- 원문: “정량 저점과 교차 대조해 근인을 규명합니다.”
- 원문 위치: 메인 기능 ‘서술형 응답 분석’
- 문제 근거: 전문용어가 겹치고, 화면에서 설명한 분석 과정보다 강한 원인 확정으로 읽힐 수 있습니다.
- 적용 원칙: ③ 사용자 언어, ⑤ 확인된 사실
- 수정안: “점수가 낮은 항목과 서술형 의견을 함께 살펴, 개선이 필요한 이슈를 파악하도록 돕습니다.”
- 확인할 사항: 실제 분석 방식과 원인 추론의 근거·한계.
- 검증 방법: 무엇이 관찰된 결과이고 무엇이 추정인지 독자가 구분하는지 확인합니다.

### COPY-007 · 자료 신청이라는 다음 행동을 예고하기

- 상태: 검토 제안
- 우선순위: 중간
- 원문 ID: D-228 및 같은 영역 CTA
- 원문: “자료 다운로드” / “자료 받기”
- 문제 근거: 연결 화면은 기업·담당자 정보를 받는 소개서 신청서입니다. 즉시 파일 열람을 기대할 수 있습니다.
- 적용 원칙: ④ 다음 행동
- 수정안: 제목 “소개서·결과지 샘플 신청”, 버튼 “자료 신청”, 보조 설명 “신청한 자료를 이메일로 받아보세요.”
- 출처: inventory의 supplemental_cta_evidence.materials. 실제 이메일 발송은 검증하지 않았습니다.
- 기대 효과 가설: 클릭 전에 정보 입력과 이메일 수령을 예상합니다.
- 검증 방법: 클릭 전 다음 화면과 수령 방법을 예측하게 합니다.

### COPY-008 · 비교 우위보다 측정 범위를 설명하기

- 상태: 사실 확인 필요
- 우선순위: 중간
- 원문 ID: S-003
- 원문: “번아웃 위험 신호를 데이터로 포착하는 가장 검증된 방법”
- 문제 근거: 비교 대상·검증 기준이 문구 가까이 드러나지 않습니다. 주장이 허위라는 판정은 아닙니다.
- 적용 원칙: ⑤ 확인된 사실
- 수정안: “스트레스 원인·반응·지지 환경·생활 습관을 함께 살펴보는 진단”
- 확인할 사항: ‘가장 검증된’이라는 비교 표현을 뒷받침할 근거의 유무.
- 기대 효과 가설: 막연한 우위보다 조사 내용을 구체적으로 판단합니다.
- 검증 방법: 이 진단이 무엇을 조사하는지 설명하게 합니다.

### COPY-009 · ‘승인’의 의미를 일관되게 설명하기

- 상태: 사실 확인 필요
- 우선순위: 중간
- 원문: “승인”, “승인 피드백 교육”
- 원문 위치: 메인 결과 예시와 액션 예시. 몰입 진단 표에는 “승인(성과 인정)”으로 설명되어 있습니다.
- 문제 근거: 결재 승인으로 읽을 가능성이 있습니다. 공식 모델명과 일반적 의미의 관계를 확인해야 합니다.
- 적용 원칙: ③ 사용자 언어, 용어 일관성
- 수정 방향: 공식 명칭 유지 시 첫 등장에 “승인(성과 인정)”을 병기합니다. 명칭 변경이 허용되면 “성과 인정” 등으로 통일하는 안을 검토합니다.
- 검증 방법: 해당 결과 항목이 무엇을 의미하는지 묻습니다. 독자의 오해는 아직 관찰하지 않았습니다.

## 구조·정책·동작 사항은 별도로 관리

아래는 문장 표현만으로 확정하거나 해결하기 어려운 사항입니다. 카피의 품질 판단과 구분합니다.

| 구분 | 확인 사항 | 상태 |
|---|---|---|
| 구조 | 메인에서 진단 7종을 비교하기 전에 긴 상세를 읽게 되는 구성 | 별도 구조 검토 후보 |
| 서비스 설명 | 첫 화면의 3분과 본조사·정기 설문의 시간 구분 | 적용 범위·시간 안내 확인 필요 |
| 모델 | 스트레스 점수의 높고 낮음에 대한 설명 충돌 | 지표별 방향 확인 필요 |
| 성과 근거 | 실명 성공사례와 재구성 예시의 관계 | 실제 성과·예시 범위 확인 필요 |
| 요금 | 월 정액 설명과 구매 요약의 과금 기간 표시 | 최종 과금 정책 확인 필요 |
| 지원 범위 | 컨설턴트 동행과 플랜별 포함 범위 | 정책 확인 필요 |
| 체험 절차 | 신청 후/승인 후 발급 및 담당자 연락의 관계 | 정책 확인 필요 |
| 콘텐츠 연결 | 몰입 리포트 12개 화면 예고와 관찰한 6개 화면 | 제공 범위 확인 필요 |
| 동작 | 환불정책 링크에서 본문을 확인하지 못함 | 별도 연결 점검 필요 |

## 운영 방법

1. writing-guide.md를 읽고, inventory에서 해당 문구와 주변 맥락을 확인합니다.
2. 원문을 덮어쓰지 않고 review에 수정안을 기록합니다. 원문 수집을 갱신하면 수집 시점과 변경 이력을 남깁니다.
3. 서비스 기능·정책·공식 용어를 확인해야 하는 문구는 사실 확인 필요로 유지합니다.
4. 문안을 확정하고 홈페이지에 반영한 뒤 실제 화면과 표시 조건을 확인합니다.
5. 확정된 카피와 흐름에 맞춰 기존 E2E 테스트를 수정합니다. 이해와 설득의 품질을 단순 문자열 일치 검사로 판정하지 않습니다.
6. 실제 사용자 검증의 결과는 전문가의 예상과 분리해 기록합니다.

## 수집 한계

14개 표시 상태의 2,641개 위치별 기록을 사용합니다. 상태별 중복과 이미지 대체텍스트를 포함한 수이며, 서로 다른 문구 수가 아닙니다. 이미지 안 글자는 전사하지 않았습니다. 자동·로그인·제출 후 팝업의 전체 범위를 확인한 것은 아닙니다. 개별 페이지 전체 QA 및 운영 기능·성과 검증은 완료하지 않았습니다.
